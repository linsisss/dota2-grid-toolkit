# Telegram, файлы и лайки

Аватары: [Telegram getUserProfilePhotos](https://core.telegram.org/bots/api#getuserprofilephotos) и [getFile](https://core.telegram.org/bots/api#getfile). Файл скачивает только backend; URL с токеном не используется в HTML или ответах API.

Локальная реализация, без production build и выкладки. Вход необязателен для редактора, импорта, скачивания и публикации. Серверные файлы и лайки требуют входа. Редактирование уже опубликованной сетки требует привязки к вошедшему аккаунту.

## Вход

`AccountProvider` на `/editor` и `/catalog` читает `/api/catalog/auth/me`. По клику сразу открывается окно Telegram; после POST `auth/start` оно переходит в `https://t.me/grid_studio_bot?start=login_<id>`. Если браузер заблокировал окно, в диалоге остаётся прямая ссылка. Пользователь нажимает «Войти» в личном чате бота. Сайт опрашивает статус и автоматически отправляет POST `auth/finish`. Кодов, сверки и второго подтверждения на сайте нет. Telegram при первом запуске бота может показывать собственную кнопку «Начать».

`server/accounts.mjs` создаёт одноразовую попытку на 5 минут: случайный ID 192 бит, отдельный verifier 256 бит в HttpOnly cookie `gs_login`. Бот получает только ID. В SQLite хранится хеш verifier, сессии тоже хешируются. Подтверждение принимается от того же человека в приватном чате, от актуальной карточки именно нашего бота; первый кандидат закрепляется за попыткой. Старые, чужие, отменённые и использованные попытки отклоняются. Origin/JSON-проверки действуют для начала и завершения входа. Это защищает привязку браузера без ручной сверки кода.

Сессия `gs_account`: HttpOnly, SameSite=Strict, Secure при HTTPS, path `/api/catalog`, 30 дней. Выход отзывает её на сервере. Ключи не попадают в localStorage, ответы API или ссылки. Сервер хранит Telegram ID, отображаемое имя, username и доступную боту аватарку. С 2 октября 2026 года интерфейс показывает не @username, а ник профиля автора (см. «Профили авторов» ниже); @username виден другим, только если владелец включил это в настройках профиля. Фото получаем через getUserProfilePhotos/getFile, уменьшаем до 96×96 PNG и храним в account_avatars; /auth/avatar отдаёт только фото вошедшего пользователя. В браузер не передаётся URL с токеном бота. Отсутствие фото даёт заглушку, ошибка получения не мешает входу. Телефон не запрашивается. Бот обрабатывает вход в существующем worker, отдельный polling-процесс на тот же токен создавать нельзя. `CATALOG_TELEGRAM_BOT_USERNAME` должен соответствовать токену (по умолчанию grid_studio_bot). Членство в чате нужно для модерации, но не для входа на сайт.

## Файлы

Кнопка лендинга «Создать свою сетку» ведёт на `/editor?new=1` (либо `editor.html?new=1` при соответствующем Vite entry). `enterWorkspace` создаёт отдельный пустой native-файл, учитывает текущий аккаунт, запоминает его для вкладки и убирает параметр из URL после сохранения. Повторное выполнение эффекта React использует тот же promise. Перезагрузка открывает этот файл, обычный `/editor` сохраняет прежнее поведение навигации. Существующие документы не заменяются.

В карточках «Студии» дата изменения стоит рядом с названием файла. Подпись «В аккаунте / На устройстве» убрана; состояние синхронизации и сообщения об ошибках продолжают работать.

Компактный поиск находится слева от «Импорт файла». Ссылка в боковом меню называется «Мастерская». При выборе сетки точки остаются на месте: выбранная меняет цвет и слегка увеличивается за 140 мс; прокрутка происходит только для скрытой точки, без принудительного центрирования.

Карточка файла показывает все его сетки по очереди: точки справа, стрелки и счётчик под превью. Можно листать свайпом или клавишами со стрелками; Home/End выбирают первую/последнюю сетку. Клик по превью открывает выбранную сетку. Перелистывание само по себе не меняет файл. Для длинного списка точек есть внутренняя прокрутка. Учитываются актуальные правки и черновики каждой сетки, скрытые слои не отображаются.

`/editor` при первом открытии показывает «Студию» (до 1.6 она называлась «Мои файлы»). Обновление уже открытой вкладки возвращает в её файл и выбранную сетку; переход «Файлы» отменяет это восстановление. Проверка аккаунта завершается до открытия сохранённого места, чужие и архивные файлы не открываются автоматически. Один файл — полный native-проект с несколькими сетками, слоями и подложкой. После входа гостевые файлы автоматически привязываются к аккаунту, включая архив; кнопки «В аккаунт» нет. Они остаются теми же элементами списка, а локальные документы и резервные копии сохраняются. Новые и импортированные файлы при активном входе сразу привязаны к аккаунту. Архив обратим; это не удаление.

API `GET /spaces`, `GET/PUT/PATCH /spaces/:uuid` проверяет владельца по сессии. PUT также проверяет account и revision, поэтому смена аккаунта или одновременная правка не перезаписывают чужую/новую версию. Повтор идентичного PUT после потерянного ответа идемпотентен. Архивирование тоже сравнивает revision. Лимиты: 100 файлов (включая архив), 20 МБ на документ (8 МБ до 1.8.14), 200 МБ на аккаунт. Запрос больше 20,5 МБ сайт не отправляет, а сразу пишет, что файл не помещается в аккаунт (`maxBytes` в `catalogAPI`, `SPACE_REQUEST_BYTES` в `scripts/workspaces.mjs`): иначе он заново загружал бы весь файл после каждой правки. Поле preview в метаданных содержит только выбранную сетку и отсутствует для слишком большого JSON. Список `GET /spaces` с 1.6.1 возвращает и сетки файла (`gridNames`, `configIndex`), которые сервер запоминает при каждом PUT; у файлов, не сохранявшихся с 1.6.1, их нет до следующего сохранения.

### Превью файлов (1.6.1)

«Студия» больше не открывает документы ради карточек (`src/WorkspacePreview.jsx`, `scripts/workspace-thumbnails.mjs`). Раньше каждая видимая карточка читала файл со всеми автокопиями и копиями «Перед обновлением» (до 28 расшифровок) и рисовала тысячи подписей на основном потоке: на файлах с историей первое превью появлялось через 20 с, а клики ждали до 1,7 с.

- **Картинки.** Каждая сетка файла хранится прозрачной WebP 716 × 356 в IndexedDB `gridstudio-thumbnails`. Фон (Dota, градиент или «Мой фон») рисуется под картинкой по переключателю превью (`src/grid-ground.js`).
- **Когда рисуются.** Через 3 с после последнего сохранения в редакторе, когда браузер свободен (`scheduleThumbnails`, из `openWorkspace` → `storage.save`). Карточка узнаёт о новых картинках по событию `gridstudio:thumbnails`.
- **Старые файлы.** Если картинок нет или они старше `updated` файла в реестре, карточка сразу показывает старые, если они есть. Новые делаются в фоне по одному файлу (`makeThumbnails`): только последнее сохранение (`ProjectStorage.peek`), по сетке за задачу.
- **Файлы с другого устройства.** Если копия в аккаунте новее браузерной (`remoteRevision` ≠ `cloudRevision`, нет несохранённых правок), карточка показывает `GET /spaces/:uuid/thumbnail.webp?grid=N&revision=R`. Сервер рисует сетку этой ревизии (`server/catalog-preview.mjs` `renderSpaceThumbnail`, тот же рендер, что для Telegram и главной). В памяти он хранит 48 последних картинок, ответ кэшируется браузером навсегда: ревизия в адресе. Лимит — 240 картинок в минуту на аккаунт. Весь документ (до 20 МБ) ради превью больше не скачивается.
- **Синхронизация и кнопки.** Синхронизация с аккаунтом больше не блокирует «Создать», импорт и карточки. Индикатор — в боковой панели. На время отправки заблокированы только кнопки файла, который сейчас уходит в аккаунт. Список сначала показывает файлы браузера, данные аккаунта подтягиваются следом; строка реестра перезаписывается, только если в аккаунте что-то изменилось.

Привязка использует pendingUpload и стабильный cloudId (для legacy выдаётся UUID без смены локального ключа). Назначение владельца сохраняется до отправки. При потерянном ответе повтор использует тот же UUID; данные другого аккаунта никогда не переносятся. После сетевой ошибки повторяем при возврате в окно, появлении сети или через кнопку повтора. Повреждённые файлы остаются для восстановления. Активный редактор сначала сбрасывает автосохранение, затем подключается к аккаунту без закрытия холста. Локальные резервные копии сохраняются независимо от сервера. См. [project-storage.md](project-storage.md) и тесты `workspaces.test.cjs`. При конфликте правки остаются локально; из списка файлов можно создать копию. Не менять старые ключи и схему native-проекта при новых релизах. Серверные файлы не заменяют внешние резервные копии SQLite и скачанный пользователем native JSON.

## Профили авторов

Пользователь попросил 2 октября 2026 года: у каждого вошедшего через Telegram есть публичный профиль — ник, аватарка, описание, по желанию @username, его сетки, фоны и гайды и сколько лайков они собрали. Решения пользователя: автор сеток и фонов вошедшего — ник профиля, а поле «Автор» в формах стало «Оригинал / по мотивам»; аватарка по умолчанию — узор (фото из Telegram или своя картинка по выбору); общего списка авторов пока нет.

- **Сервер** — `server/profiles.mjs`, таблица `profiles` в базе мастерской: `account`, `key` (12 символов HMAC от соли, публичный адрес профиля), `nickname` и `folded` (ник в нижнем регистре, ё → е, уникальный), `changed` (последняя смена ника), `bio`, `telegram` (показывать ли @username), `avatar` (`pattern` | `telegram` | `custom`), `image` и `version` своей картинки, `created`.
- **Ник.** При первом входе (`accounts.finish`) и при запуске для всех, кто входил раньше (`Accounts` → `profiles.ensureAll()`), ставится свободный ник из двух английских слов (ScoutingDuck); если оба слова заняты 10 раз подряд — с двумя цифрами. Выбрать свой: 3–20 символов, латиница, кириллица, цифры и `_ . -`, хотя бы одна буква, знак не по краям, не имя сайта и не «admin», «модератор», «support» и подобные (`cleanNickname`). Менять — раз в 7 дней (`NICK_DAYS`): раньше — 429 с `nicknameAt`, занятый — 409. Первая смена после выдачи сгенерированного ника свободна.
- **Описание** — до 300 символов и 6 строк, лишние пробелы и пустые строки убираются (`cleanBio`). **Telegram** — `@username` из `accounts` попадает в публичную карточку, только когда включён.
- **Аватарка.** `GET /profiles/<key>/avatar?v=…`: узор (`patternAvatar` — SVG 5 × 5, зеркальный, цвета из HMAC ключа), фото из Telegram (`account_avatars`, берётся при входе) или своя картинка: `PUT /profile/avatar` телом файла до 5 МБ, центр квадратом → WebP 256 px без метаданных. `v` меняется со сменой картинки, поэтому ответ кэшируется навсегда; у SVG — CSP `default-src 'none'`.
- **API.** `GET/PATCH /profile` (свой профиль: ник, описание, переключатель Telegram), `POST /profile/avatar {mode}`, `PUT /profile/avatar`, `GET /profiles/<key>` — карточка, `mine`, `stats` (сетки, фоны, гайды и сумма их лайков) и по 60 последних сеток, фонов и гайдов. `/auth/me` отдаёт `nickname`, `profile` (ключ) и `avatar` профиля.
- **Подпись работ.** Сетка (`revisions.author`) и фон (`backgrounds.author`) вошедшего хранятся без подписи; в ответах у них `creator: {key, name, avatar}` и `credit` (новая колонка, «по мотивам», до 60 символов). Гостевые работы подписаны как раньше. Правка админом у работ с профилем меняет только `credit`. Поиск мастерской и админки находит работы и фоны по нику (`profiles.matching`). Гайды и комментарии показывают ник и аватарку профиля; старые ссылки `/guides/people/<key>.jpg` отдают аватарку профиля. Бот в уведомлениях подписчикам и в карточках проверки называет ник.
- **Интерфейс.** Имя автора — ссылка с аватаркой на профиль (`src/catalog/Creator.jsx` `CreatorName`, гайды — `Author` в `src/guides/GuideParts.jsx`). Профиль — `/workshop?creator=<key>` (`src/catalog/CreatorProfile.jsx`): шапка с аватаркой, ником, Telegram, датой, описанием и счётчиками, вкладки «Сетки / Фоны / Гайды». Кнопка аккаунта открывает выпадающее меню, не окно (`AccountButton`; закрывается кликом мимо, Esc или выбором, ↑ ↓ — по пунктам): «Мой профиль», «Настройки профиля», «Админка» для админов, состояние сохранения файлов и «Выйти». «Настройки профиля» (`ProfileSettings.jsx`: аватарка сохраняется сразу, ник, описание и Telegram — кнопкой). В формах отправки сетки и фона у вошедшего вместо «Автор» поле «Оригинал / по мотивам» (`CreditField`).
- **Значки** (пользователь попросил 2 октября 2026 года): «Разработчик», «Bug Hunter», «Идейный вдохновитель», «Поддержавший», «100 лайков», «500 лайков» — список, подсказки и иконки (Lucide) в `scripts/profile-badges.mjs`. Первые четыре выдаёт админ: на профиле у него кнопка «Значки» (`src/catalog/Badges.jsx`), `POST /admin/profiles/<key>/badges {badge, on}`, таблица `profile_badges`, запись в «Журнал» («Значок выдан / снят: …», раздел «Профиль»). «Модератор» (с 04.10.2026) тоже вручную не выдаётся: он есть, пока у аккаунта роль модератора (таблица `moderators`, выдаётся в «Пользователях»), и пропадает вместе с ней; синий, с щитом, идёт вторым после «Разработчика». Лайковые вручную не выдаются: они считаются из суммы лайков на опубликованных сетках, фонах и гайдах автора (`creatorStats`), показывается только старший. Значки идут под ником в профиле (`badges` в `GET /profiles/<key>`), подсказка — при наведении; маленькими иконками — после ника на карточках сеток и фонов, на странице сетки, в гайдах и комментариях (`creator.badges` у каждого автора, `BadgeIcons`; лайки автора кэшируются на минуту, `profiles.likes`). Выданный значок бот присылает владельцу в личку один раз (`badge_notices`, `deliverBadgeNotices`); снятый до отправки — не присылает, повторная выдача того же значка нового сообщения не даёт.
- **Подписка из профиля:** кнопка «Подписаться на автора» на чужом профиле (`PUT /profiles/<key>/subscribe`, та же таблица `subscriptions`, что и на странице сетки, `store.follow`) — бот пишет о новых сетках автора, а с 1.8.2 и о его фонах (после одобрения) и гайдах (при первой публикации): `store.notifyFollowers(author, key)` с ключом `<id>`, `bg:<id>` или `guide:<id>`, тексты без рода («Новая сетка героев от <ник>: «название»»). Кнопка отписки в сообщении — `sub:off:p:<ключ профиля>` (старая `sub:off:<id сетки>` работает).
- **Превью ссылки на профиль** (с 1.8.2): `/workshop?creator=<key>` nginx отдаёт API (`/api/catalog/page/workshop`), страница получает Open Graph с ником и описанием и картинку `GET /api/catalog/preview/profile/<key>.jpg` (1200 × 630, `profilePreviewImage` в `server/link-preview.mjs`: аватарка, ник, значки, счётчики). Шрифт превью — Libre Franklin из `assets/dota-fonts` (Montserrat убран в 1.8.0, и превью рисовались запасным шрифтом).
- **Аватарки команды на главной** (с 1.8.2) — из профилей: `GET /api/catalog/team` отдаёт аватарки аккаунтов команды (`TEAM` в catalog-api), `LandingGallery` берёт их вместо картинок из сборки, а без ответа остаётся на них.
- **Сообщения бота и их выключатели** (попросил пользователь 3 октября 2026 года): виды — `scripts/profile-notifications.mjs` (`review` — одобрение и отклонение сеток, фонов, артов и гайдов; `comments` — новый комментарий к своему гайду, сетке или фону; `replies` — ответ на свой комментарий; `follows` — новое у авторов из подписок; `badges` — выданный значок). Все включены, пока их не выключат: выключенные хранятся в `profiles.muted` (через запятую), `GET /profile` отдаёт `notifications: { вид: bool }`, `PATCH /profile { notifications: { вид: bool } }` меняет (неизвестный вид — 400). В «Настройках профиля» — блок «Сообщения от бота в Telegram», каждый флажок сохраняется сразу. Бот проверяет вид перед каждым сообщением (`direct(…, kind)`): выключенный — строка очереди становится `muted`, сообщение не уходит. Под сообщениями о комментариях кнопка «Не присылать такие» (`nt:off:<вид>`, только в личке с ботом) выключает этот вид.
- **Сообщения о комментариях** — `server/comment-notices.mjs`: при новом комментарии к гайду (`guides.comment`), сетке или фону (`ItemComments.add`) в `comment_notices` попадают автор работы (`comment`) и автор комментария, на который ответили (`reply`); одному человеку — одно сообщение (ответ автору — `reply`), о своих словах — ничего. `deliverCommentNotices` пишет «Новый комментарий к твоему гайду «…» от <ник>» / «<ник> — ответ на твой комментарий к …» с цитатой (до 400 символов) и кнопкой на сам комментарий: `/guides?id=…#comment-<id>`, `/workshop?id=…#comment-<id>`, у фона — `/workshop?backgrounds&comments=<id>` (окно комментариев открывается само). Комментарий удалили до отправки или работа скрыта — сообщения нет. Страница по `#comment-<id>` прокручивает к нему и подсвечивает (`Comments.jsx`).
- **«Пользователи» в админке** (с 03.10.2026): `GET /api/catalog/admin/users?q=&sort=new|seen|works&source=&offset=` (`server/admin-users.mjs`, `src/catalog/AdminUsers.jsx`, только админам) — все из `accounts`: профиль (ник, аватарка, значки, `profiles.created`), Telegram (имя, @username, id, показывает ли профиль Telegram), последний заход (`visits.last` из статистики, иначе последний вход), опубликованные сетки, фоны, гайды и арты, видимые комментарии, действующее ограничение (`blocks` `account:<id>`). Поиск без учёта регистра по нику, @username, имени и id; по 50. ## Публикации и популярность

POST `/works` доступен гостю с обычной проверкой ALTCHA и квотами. При активном входе новая публикация получает владельца account. Старую гостевую сетку можно привязать POST `/manage/:id/claim`: нужны одновременно секретный ключ публикации и сессия. После привязки ключ без аккаунта не разрешает управление. Изменение опубликованной сетки без привязки запрещено; непубликовавшуюся гостевую заявку можно править по ключу. `/mine` выдаёт только собственные публикации.

Квота за скользящие 24 часа: 3 отправки без входа, 10 для Telegram-аккаунта, включая обновления. Аккаунт учитывается по серверной сессии, а не из тела запроса. Его история берётся из аудита, включая привязанные гостевые и удалённые работы; смена браузера не даёт новую квоту. Общий лимит сети 60 отправок сохраняется. 429 сообщает конкретную причину и время до следующей доступной отправки.

PUT `/works/:id/like` принимает `{liked:true|false}`, требует сессию и опубликованную активную сетку. Уникальная пара (work,account) исключает повторные лайки. В каталоге `sort=popular` сортирует по числу лайков, затем дате публикации и ID; `liked` персонализирован, публичные ответы не кешируются между пользователями. Лайки не отменяют премодерацию и не гарантируют защиту от владельцев нескольких Telegram-аккаунтов. Прежние поля featured оставлены в SQLite для совместимости, в интерфейсе подборки авторов больше нет.

Свою работу лайкнуть нельзя (с 1.6.1): если аккаунт вошедшего совпадает с `works.account` (у фонов — `backgrounds.account`), `store.like` и `CatalogBackgrounds.like` отвечают 403 «Свою работу лайкнуть нельзя.»; снять лайк можно всегда. Гостевые работы без аккаунта ничьи, второй аккаунт того же человека не распознаётся. В интерфейсе кнопка лайка (`LikeButton` в `src/catalog/Account.jsx`) на своей работе (`mine` — у сеток из `publicItem`, у фонов из `CatalogBackgrounds.view`, для каждого пользователя свой) показывает число лайков, но неактивна, с подсказкой «Свою работу лайкнуть нельзя». Привязка гостевой сетки (`/manage/:id/claim`) в той же транзакции удаляет лайк привязавшего аккаунта на ней. Лайки, поставленные авторами себе раньше, удаляются при запуске: `CatalogStore` — у сеток, `CatalogBackgrounds` — у фонов (`store.removeSelfLikes`). Удаляются только строки, где оба аккаунта заданы и равны. Запуск, который что-то удалил, пишет одну строку аудита: `work` = NULL для сеток или `bg:*` для фонов, `action` = `likes:self-removed:<число>`, `actor` = NULL. Эти строки не совпадают ни с одной работой, поэтому не влияют ни на квоту отправок аккаунта, ни на карточки Telegram. API и бот могут стартовать одновременно: удаление идёт под `BEGIN IMMEDIATE`, поэтому второй запуск ничего не находит и строку не пишет; повторные запуски тоже ничего не меняют.

## Проверка и эксплуатация

- `npm run check`, `npm test`: авторизация, cookies, ограничения, чужие аккаунты, одноразовый вход, привязка, лайки (в том числе запрет лайка своей работы и очистка, `self-likes.test.cjs`), private API, конфликты, сохранение старого проекта и namespace резервных копий.
- Автотесты используют подставной Telegram API и временные/in-memory базы; заявки в рабочий чат не отправляют.
- Локально: `npm run dev` и один `npm run catalog:bot`. Полный реальный вход пользователь завершает в своём Telegram; токен не отдавать браузеру.
- Перед разрешённой выкладкой: HTTPS, локальная серверная проверка ALTCHA, постоянная SQLite с бэкапами, API + worker, увеличенный proxy body limit только для private spaces, запрет логирования cookies/тел запросов. См. [catalog.md](catalog.md) и [releases.md](releases.md).

# Мастерская (каталог сеток)

С 1.5 раздел в интерфейсе, у бота и на лендинге называется «Мастерская». Страница — `/workshop`; прежние `/catalog` и `/catalog/` отвечают 301 на `/workshop` с теми же параметрами (фрагмент `#manage=…` браузер переносит сам), так что старые ссылки, закладки и сообщения бота работают. В коде, API (`/api/catalog`), файле `catalog.html`, классах и базе остаётся `catalog`.

Реализован локально. Production build и публикация ещё не выполнялись. Источник данных — собственный Node API и SQLite, не localStorage пользователей. Сам редактор продолжает работать при недоступном каталоге.

## Интерфейс

Сохраняется визуальный язык Focus: фон #15141a, панель #211e29, текст #efeaf5, вторичный текст #afa7bf, граница #383340, акцент #c4b5ed. SF Pro Display для интерфейса, Radiance для сеток. Каталог — галерея работ, модерация — рабочий инструмент. На широком экране три превью в ряд, на телефоне одно; у карточки название, автор и число категорий, без выдуманных рейтингов. Публикация — защищённый диалог с превью слева и формой справа, на телефоне последовательно.

- Главная кнопка «Мастерская» открывает `/workshop` (`catalog.html` для статического хостинга).
- Правила мастерской — `/workshop?rules` (`src/catalog/Rules.jsx`): ссылка в подвале и в форме публикации («Отправляя сетку, ты принимаешь правила»). Сетки не считаются чьей-то собственностью, жалобы на копирование не рассматриваются; запреты (в первую очередь сексуализация несовершеннолетних), реклама только TikTok/Twitch/YouTube, решения операторов окончательные. Правила применяются модераторами вручную, автоматической проверки нет.
- В редакторе «Экспортировать» → «Опубликовать в мастерскую». Передаётся только активная видимая сетка. Остальные сетки, скрытые слои, черновики, подложка и неизвестные поля не передаются.
- Название обязательно, автор необязателен, до трёх тегов. Публиковать можно без входа. Гостю выдаётся секретная ссылка, которая сохраняется в «Моих публикациях» браузера. После входа новые публикации привязываются к Telegram-аккаунту.
- Каталог: поиск по названию/автору без учёта регистра, теги, новые работы, «Популярные» по числу лайков, пагинация. Лайки доступны после входа через Telegram, один лайк на аккаунт и сетку, его можно снять. «Выбор авторов» удалён. Превью рисуется из проверенного JSON общими функциями игрового рендера; сервер не принимает стороннюю обложку.
- Инструкция «Как установить» (`src/catalog/InstallGuide.jsx`) открывается из шапки мастерской и со страницы сетки: скачать, закрыть Dota 2 и сохранить копию старого файла (или добавить сетку к своему файлу через редактор), найти папку `userdata\<ID>\570\remote\cfg` по ссылке Steam или коду друга, положить файл и выбрать сетку в игре. Поиск папки общий с инструкцией экспорта редактора (`findSteamAccount` в `scripts/steam-folder.mjs`); профиль и папка хранятся только в памяти страницы.
- Страница работы: скачивание одной сетки и открытие в редакторе. Редактор сначала предлагает добавить её к текущим сеткам, сохраняет рабочий документ, поддерживает отмену. Подмена текущего проекта при переходе по ссылке исключена.
- Изменение уже опубликованной сетки требует входа и привязки к Telegram. Старая гостевая ссылка позволяет привязать сетку один раз; после привязки ключ без аккаунта перестаёт давать доступ. До первой публикации гостевая заявка редактируется по ключу. Обновления проходят повторную модерацию: новая версия приватна, прежняя остаётся публичной. Удаление требует подтверждения.
- Жалобы отправляются с ALTCHA, видны только модератору; повтор от одного браузера объединяется. Комментариев нет.
- Вход, личные файлы и лайки: [accounts-workspaces.md](accounts-workspaces.md). Бот открывается по нажатию кнопки входа; после кнопки «Войти» в боте исходная вкладка подключает аккаунт автоматически, без кодов и второго подтверждения.

## Локальный запуск

API также обслуживает поиск Steam-профиля из инструкции экспорта: `/steam/resolve`. Необязательный `STEAM_WEB_API_KEY` хранится только на сервере, без него используется публичный XML Steam. См. docs/steam-folder.md.

Node.js 22.19+ (используется встроенный `node:sqlite`). Дополнительная СУБД не нужна. Серверное PNG-превью использует @napi-rs/canvas, Telegram-модерация — puregram; оба пакета находятся в production dependencies.

```sh
npm run catalog:setup
npm run dev
```

Setup создаёт **только если файла ещё нет** игнорируемый `.env.catalog.local`: серверный секрет, локальный origin и резервный ключ веб-модерации (сама веб-модерация выключена). Значения не печатаются. `npm run dev` поднимает Vite на 4173 и API на 4174. Для других портов — `STUDIO_PORT` и `CATALOG_PORT`. Самостоятельный API: `npm run catalog:serve`.

Модерация выполняется **через Telegram**, бот @grid_studio_bot, чат `-1004309207941`, топик **6 — approve grids here** ([ссылка](https://t.me/c/4309207941/6)). В отдельном терминале:

```sh
npm run catalog:bot -- --check
npm run catalog:bot
```

`--check` только проверяет бота, форум, права администратора и отсутствие чужого webhook; сообщений не отправляет. Бот использует `CATALOG_TELEGRAM_BOT_TOKEN` либо `TELEGRAM_BOT_TOKEN`. Для существующей локальной установки токен берётся из игнорируемого `.env.release.local`, если его нет в окружении. Копировать токен не требуется. На сервере задавать токен через защищённое окружение.

`npm run dev` не запускает Telegram-процесс автоматически: обычная разработка и тесты не должны рассылать сообщения в рабочий чат. Для проверки своими локальными заявками запусти `catalog:bot` отдельно; карточки помечены «Локальная проверка» и меняют только локальную базу. Не запускать local и production polling одновременно с одним токеном.

Карточка содержит PNG 1193×593 и подпись по образцу пользователя: «Новая сетка на проверку: \"название\"», автор, количество категорий и теги. До решения показано «Ожидает принятия решения», после — результат, имя участника и Telegram ID. Кастомные эмодзи: уведомление `5879813604068298387`, автор `5920344347152224466`, категории `5960551395730919906`, теги `5886436057091673541`, одобрение `5985596818912712352`, отказ `5985346521103604145`, ожидание `5776213190387961618`. Подпись использует HTML `tg-emoji`, кнопки «Одобрить» / «Отклонить» — `icon_custom_emoji_id` с теми же галочкой/крестиком. Нет счётчиков героев/символов и технического номера заявки в подписи; они остаются в данных. Предупреждение о более чем 2 000 категориях, текст жалобы и маркировка локальной проверки сохраняются.

PNG строится **на сервере из проверенного JSON** с теми же функциями разметки, Radiance и портретами из репозитория. Обложки от пользователя, URL ресурсов и секретные ссылки управления не используются. Шрифтовые fallback на разных ОС могут отличаться от браузера и игры. Форматирование соответствует [Telegram HTML](https://core.telegram.org/bots/api#html-style), иконки кнопок — [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton). Telegram разрешает custom emoji ботам с дополнительным именем Fragment либо в прямых сообщениях бота в личные/групповые чаты при Premium у владельца. Проверка этого оформления выполняется локальными тестами API payload без отправки сообщений в рабочий чат.

Любой текущий участник чата (не только администратор) вправе принять решение. Каждый callback проверяет чат, топик, отправителя карточки, её ID и актуальное членство пользователя через getChatMember. Restricted-пользователь допускается только при is_member=true; left/kicked/боты отклоняются. При невозможности проверить членство решение не принимается. Сам бот должен быть администратором для надёжной проверки участников.

Решение сохраняется транзакционно вместе с Telegram ID и именем проверившего. После первого нажатия карточка показывает результат и автора решения, кнопки исчезают. Повторный клик не меняет решение. Отказ записывает автору причину «Отклонено участником команды в Telegram». Новая версия требует новой карточки; старая кнопка её не одобрит. Секретный ключ публикации не передаётся в Telegram.

Жалобы также поступают в этот топик: «Оставить сетку» отклоняет жалобу, «Скрыть сетку» убирает работу из публичного каталога. Решение относится к просмотренной публичной версии; новая версия не одобряется автоматически.

Админка на сайте — `/workshop?moderate`. Её открывают только Telegram-аккаунты из `CATALOG_ADMIN_TELEGRAM_IDS` (через запятую); без списка вход закрыт для всех. Пароля нет: сервер на каждом запросе `/admin/*` проверяет сессию `gs_account` и её Telegram ID (без входа — 401, чужой аккаунт — 403), `/auth/me` сообщает `admin`, чтобы показать ссылку. Вкладки «На проверке», «Жалобы», «Опубликованы», «Заблокированы» со счётчиками; одобрение, отказ с причиной, подборка, закрытие жалоб, блокировка (в том числе IP) и разблокировка, пауза приёма. Действие `edit` (`title`, `author`, `tags`, те же правила `catalogMeta`, что и у публикации) правит опубликованную ревизию или ожидающее обновление на месте, без повторной проверки; имя сетки в JSON следует за названием. Кнопка правки видна админам на карточках галереи, на странице работы и в админке. Каждое действие записывается в `audit.actor` (ID и имя админа); карточка в Telegram-топике показывает решение, принятое на сайте, и его автора.

ALTCHA включена и локально, и в production. Виджет altcha 3.2.3 и библиотека altcha-lib 2.5.0 включены в зависимости: скрипт и challenge загружаются с того же origin, внешние CAPTCHA/CDN не используются. Регистрация и ключи стороннего сервиса не нужны. Проверка запускается в фоне только в формах публикации, обновления заявки и жалобы; редактор и скачивание от неё не зависят.

## Сервер и данные

- `server/catalog-api.mjs`: HTTP-маршруты `/api/catalog/*`, origin/тип/размер запроса, cookie и сессии.
- `server/catalog-captcha.mjs`: одноразовые ALTCHA PoW-задания, криптографическая проверка, срок действия и постоянный реестр использования.
- `server/catalog-store.mjs`: транзакции SQLite/WAL, опубликованная и проверяемая ревизии, квоты, жалобы, журнал модерации.
- `server/catalog-telegram.mjs`: отдельный puregram polling worker, проверка членства и inline callbacks.
- `server/catalog-telegram-store.mjs`: SQLite-очередь карточек, квитанции сообщений, offset и lease одного worker.
- `server/catalog-preview.mjs` + `scripts/catalog-rendering.mjs`: PNG на сервере и общий браузерный рендер.
- `scripts/catalog-document.mjs`: общий allowlist JSON, лимиты и безопасное извлечение/добавление одной сетки.
- `src/catalog/`: клиент каталога, публикация, управление, модерация, детерминированное превью.

База по умолчанию `.catalog-data/catalog.sqlite`, можно задать `CATALOG_DB`. Не размещать её в `dist`, web root или папке сменяемого релиза. Данные должны жить вне директорий сборок. База, SQLite WAL/SHM, локальный секрет и env исключены из Git и проверки релизов. Для бэкапа использовать SQLite online backup либо останавливать API и копировать базу с учётом WAL; копия одного открытого файла `.sqlite` не является надёжным бэкапом. Проверять восстановление отдельно перед запуском на сервере. Удаление работы убирает ревизии из рабочего каталога; прежние серверные бэкапы имеют свой срок хранения.

`works` хранит ссылки на публичную и текущую проверяемую ревизии. Апдейт создаёт новую заявку, не меняя публичную запись. Модератор отправляет ID просмотренной ревизии: если автор изменил заявку, сервер возвращает 409 и требует перечитать очередь. Аналогичная защита есть при редактировании из двух вкладок. Создание имеет клиентский случайный ID и 256-битный ключ: безопасный повтор после потерянного ответа возвращает существующую заявку вместо дубликата. Ключ хранится в браузере до отправки. На сервере сохраняется только SHA-256 ключа; IP и браузерный идентификатор — HMAC с серверным секретом. Не менять `CATALOG_SECRET` при каждом релизе: он нужен для стабильности cookie и квот.

Секрет управления находится во фрагменте `#manage=…`, не в query/path, и передаётся API в Authorization. Referrer-Policy: no-referrer. Без ключа сервер не выдаёт ожидающую/отклонённую сетку. Публичный ответ не содержит ключей, источников, жалоб или черновиков. Потерянную ссылку после очистки браузера восстановить без аккаунта невозможно. Не добавлять стороннюю аналитику или запись тел запросов/Authorization на страницах управления. ALTCHA собирается локально и не загружает внешний исполняемый код. UI-шрифт по-прежнему загружается с CDNFonts.

## Ограничения и защита

- Публикация: максимум 2 МБ на запрос, одна сетка v3, 5 000 категорий (число символов не ограничено: карточка показывает его, игрок решает сам), 500 портретов, до 2 000 символов в названии одной категории. Нечисловые, отрицательные, бесконечные координаты и недопустимые ID отклоняются. Неизвестные поля удаляются; пробелы и Unicode рисунка сохраняются. Для личных файлов отдельный лимит: 8 МБ на native-документ, 8,5 МБ на PUT-запрос.
- Гостям три создания/обновления за скользящие 24 часа на подписанную cookie браузера; вошедшим через Telegram — десять на аккаунт независимо от браузера; дополнительно 60 с IP. Квота общая для создания и изменений, удаление её не возвращает. Квота аккаунта считается по существующему `audit.action='submit'` и `works.account`: учитываются старые, привязанные и удалённые публикации; обновление приложения и перезапуск не сбрасывают историю. Неудачные сохранения и повторы с квитанцией не расходуют квоту. Очередь ограничена 5 000 заявками. Ограничены частые запросы, попытки входа и жалобы.
- Доверенные авторы: Telegram ID из `CATALOG_UNLIMITED_TELEGRAM_IDS` (через запятую, в `catalog.env`) не имеют лимита аккаунта на отправки; лимит сети (60 с IP за сутки) остаётся. С 1.6.
- Ошибки 429 различают `submission_guest_limit`, `submission_account_limit`, `submission_network_limit` и общий `rate_limited`. Текст содержит причину и оставшееся время; JSON `retryAfter`/`retryAt` и заголовок `Retry-After` указывают реальное время освобождения ближайшего места, а не полные 24 часа при каждой попытке.
- Дедупликация SHA-256 нормализованного содержимого без имени файла/сетки и без зависимости от порядка категорий; повтор не создаёт карточку. Похожие, но изменённые изображения всё равно требуют модерации.
- Проверка Origin на всех мутациях, JSON-only, SameSite=Strict cookie, серверная проверка ALTCHA с привязкой к подписанной cookie браузера и назначению submit/report. Задания действуют 10 минут, использованное решение атомарно помечается в SQLite и не принимается повторно даже после перезапуска. Подписи задания и решения используют отдельные HMAC-ключи, выведенные из CATALOG_SECRET. На запросы заданий действуют отдельные квоты; клиент не может подменить сложность. Отсутствие или ошибка проверки блокирует отправку, включая локальный режим. Секреты только на сервере.
- IP — дополнительный сигнал, браузерную cookie можно сбросить. Это уменьшает спам, но не заменяет премодерацию и инфраструктурные лимиты reverse proxy.
- Чтение (GET, 600 запросов в минуту с IP) ограничивается скользящим окном в памяти процесса API (`CatalogStore.burst`): просмотр страниц ничего не пишет в SQLite, перезапуск сбрасывает только это окно. Квоты публикаций, входа, жалоб, лайков и мутаций остаются в таблице `limits`; строки старше суток удаляются не чаще раза в минуту.

## Подписки на авторов

- `PUT /works/:id/subscribe {subscribed}` (нужен вход через Telegram) подписывает на автора сетки. Автор — Telegram-аккаунт, к которому привязана работа; гостевые работы подписки не поддерживают (409), на себя подписаться нельзя. ID аккаунта автора наружу не отдаётся: карточка содержит только `followable` и `subscribed`.
- Таблица `subscriptions(account, author)`; при первом одобрении новой работы автора (`moderate` → approve без прежней публичной ревизии) в `notifications` ставится по одной записи на подписчика (`UNIQUE(account, work)`). Обновления опубликованных работ не уведомляют.
- Telegram worker отправляет очередь личными сообщениями не чаще ~25 в секунду: ссылка на сетку и кнопка «Отписаться от автора» (`sub:off:<id работы>`, работает только в личном чате самого подписчика). 429 откладывает отправку, 4xx (бот заблокирован) помечает запись `failed`, сетевые ошибки повторяются с паузой.

## Готовые арты от игроков

- В библиотеке «Готовые арты» (вкладка ASCII редактора) кнопка «Предложить свой арт» открывает форму (`src/ArtSubmission.jsx`): текст арта, превью в масштабе холста 1193 × 593, название (до 60), категория из `ART_CATEGORIES`, автор (до 40), ALTCHA с действием `art`. Правила текста общие для формы и сервера — `scripts/art-document.mjs`: как при вставке (`artLines`) убираются пустые края и общий отступ; до 120 строк, 250 символов в строке и 12 000 символов, без управляющих символов.
- `POST /arts` проверяет арт до капчи, затем `CatalogArts.submit` (`server/catalog-arts.mjs`): пауза приёма, блокировки источника, дубли (по SHA-256 текста среди ожидающих и одобренных и среди встроенных артов из `data/ascii-arts.json`), лимиты 5 в сутки на браузер без входа / 15 на аккаунт / 40 на сеть, не больше 1000 ожидающих.
- Таблица `arts` (`status`: pending → approved / rejected, approved ⇄ hidden). `GET /arts` отдаёт одобренные арты с `ETag` и `Cache-Control: no-cache`: редактор при каждом открытии получает 304, пока ничего не менялось. В библиотеке они идут после встроенных, с фильтром «От игроков»; без API остаётся встроенная библиотека.
- Модерация: карточка `kind='art'` в Telegram-топике (превью `renderArtPreview`, кнопки «Одобрить» / «Отклонить», у арта нет публичной страницы, поэтому после решения кнопок нет) и вкладка «Готовые арты» в админке (`/workshop?moderate=arts`, `GET /admin/arts`, `POST /admin/arts/:id` с `approve`, `reject`, `hide`, `restore`, `edit`). Решения сайта видны на карточке с именем администратора. В журнале арт записывается как `art:<id>`.
- Автору, вошедшему через Telegram, бот один раз пишет об одобрении (`art_notices`, те же повторы и ошибки, что у подписок).
- Превью на сервере: у Radiance нет многих символов, а Arial на сервере не установлен, поэтому `catalog-preview.mjs` подставляет системный DejaVu Sans вместо Arial из стека шрифтов.
- Символы, которых Dota не показывает (брайль, рамки, блоки, несколько эмодзи — `invisibleWarning`), в арте не принимаются (`artText`), в форме это видно сразу.

## Уведомление автору об одобрении

- Если работа привязана к Telegram (отправлена после входа или привязана позже со страницы управления), одобрение каждой версии — на сайте или кнопкой в топике — ставит одну запись в `author_notices` (ключ — ревизия; `first` отличает первую публикацию от обновления).
- Worker пишет автору в личку: «Твоя сетка «…» одобрена и опубликована в мастерской» или «Изменения в сетке «…» одобрены — в мастерской уже новая версия», с кнопкой «Открыть в мастерской». Перед отправкой проверяется, что эта версия всё ещё публичная и работа не скрыта; иначе запись `dropped`, поэтому при двух быстрых одобрениях приходит одно сообщение. Повторы и ошибки — как у подписок.
- Гостевые работы без привязки уведомлений не получают. Отказы автору не пишутся: причина видна на странице управления.

## 18+ и правка заявок

- Сетки с тегом 18+ в мастерской и на странице работы размыты до подтверждения возраста; ответ хранится в `localStorage` (`gridstudio.catalog.adult.v1`) и действует на все такие сетки. Размытие — только интерфейс: данные сетки публичны, как и раньше.
- Страница управления заявкой ведёт в редактор (`/editor?catalog=<id>&manage=1`): сетка черновика открывается по ключу из этого браузера или по аккаунту. Окно публикации предлагает «Новая публикация» или «Обновить «…»» для своих работ (сначала отклонённые и ожидающие); открытая из каталога заявка выбрана заранее (`sessionStorage`). Обновление идёт тем же `PATCH /manage/:id`.

## Сетка на главной

`store.landingWork(except)` выбирает случайную (`ORDER BY random()`) публичную активную сетку, у которой не меньше `LANDING_LIKES` = 3 лайков, без тега 18+ и без непроверенных жалоб. `except` — сетка, которую этот браузер видел в прошлый раз: она пропускается, пока есть другая, поэтому при обновлении страницы картинка меняется. Поле `works.featured` («подборка» модераторов) здесь ни при чём.

- `GET /api/catalog/landing?except=…` → `{ item: { id, revision, title, author, likes, image, srcset } | null }`, `Cache-Control: no-store` — каждый заход выбирает заново. JSON сетки на лендинг не отдаётся.
- `GET /api/catalog/landing.webp?id=…&revision=…&w=1440|2160|2880` — сетка, открытая в редакторе, в пропорциях экрана сцены лендинга 1280:675, `server/editor-showcase.mjs`. Снимки редактора сделаны в окне 1440 × 760 с плотностью 2: на экране сцены (820–950 CSS px) интерфейс остаётся читаемым, а при окне 1920 px его текст сжимался до 5–6 px и расплывался. Картинка рендерится в 2880 × 1520 и уменьшается до 2160 и 1440; лендинг выбирает размер через `srcset`, поэтому браузер не сжимает большую картинку на лету в 3D-сцене. Основа — два снимка настоящего редактора (`assets/landing/editor-rows.webp` с включёнными кнопками и образцами строк слоёв, `editor-template.webp` с пустыми холстом и списком) и замеры в `editor-template.json`. Поверх рисуются сетка на холсте (как в редакторе: портреты без приглушения), её имя в «Сетки в файле» и над холстом, «Категорий N», число объектов и список слоёв из самой сетки: «Декор» (текстовые строки, затем «Символы N»), «Герои» (группы с числом героев), «Фон». Интерфейсный шрифт — Inter, как на снимке (системный на сервере; без него Arial/DejaVu). Рендерится только сетка, которая может попасть на главную (`store.landingEligible`), один раз на ревизию для всех размеров (кэш в памяти API на 24 сетки, ~0,4 с на сетку; 80–200 КБ на размер); для другой сетки — 404, для другого `w` — 400. При совпадении ревизии `Cache-Control: public, max-age=86400`.
- После заметных изменений интерфейса редактора снимки переснимаются: `npm i --no-save playwright-core && node scripts/capture-editor-template.cjs https://dev.gridstudio.me`, затем `cwebp -lossless -z 9` для обоих PNG. Плавающая панель инструментов на снимках свёрнута до иконок («Скрыть подписи»): на главной сетка важнее инструментов. Образец строк (`tests/fixtures/editor-rows.json`) маленький, чтобы все образцы строк слоёв, включая «Фон», поместились в панель снимка.
- Лендинг (`src/landing/StageArtwork.jsx`) запрашивает сетку после загрузки страницы (с `except` из `localStorage` `gridstudio.landing-grid`), дожидается картинки и плавно показывает её поверх скриншота редактора; подпись «♥ N «Название» — автор · из мастерской» ведёт на страницу сетки. Без сетки или при ошибке остаётся скриншот.

## Нагрузка и кэширование

- Карточки каталога берут сетку через `GET /works/:id/grid?revision=N` — сохранённый JSON без лайков и без повторной сериализации. Ревизия неизменяема: при совпадении `revision` с публичной ответ получает `Cache-Control: private, max-age=31536000, immutable`, иначе отдаётся текущая сетка с `no-store`. Новая версия после модерации получает новый номер ревизии в списке, поэтому кэш не показывает устаревшую сетку. Клиент дополнительно держит до 24 сеток в памяти, чтобы смена фильтра или страницы не скачивала их снова. Страница работы по-прежнему использует `GET /works/:id` (лайки, «моя»).
- Reverse proxy не должен добавлять свой `Cache-Control` к `/api/catalog/`: API сам отдаёт `no-store` по умолчанию, а второй заголовок отменит кэш сеток. JSON сеток сжимается в 15–20 раз, поэтому на proxy нужен gzip для `application/json` (пример в README).
- `/auth/me` запрашивается при открытии страницы, при восстановлении сети и при возврате на вкладку, если с прошлой проверки прошло больше 5 минут. Вход и выход в другой вкладке сообщаются сразу через `BroadcastChannel('gridstudio-auth')`.
- Корейский шрифт Dota (1,2 МБ) редактор запрашивает сразу, чтобы измеренные интервалы хангыля не зависели от запасного шрифта; превью каталога — только для сеток с хангылем.

## Перед разрешённой выкладкой

Теги для новых заявок, редактирования и фильтров: «Аниме», «Милота», «18+», «Рамки», «С упором на героя», «Мемы», «Dead inside» (до трёх). Существующие публикации не переписываются массово; при редактировании доступны только актуальные теги. На всех экранах каталога (форма, опубликованная сетка, управление и модерация) показаны герои и категории, без счётчика символов. Успешная ALTCHA скрывается; ожидание/ошибка и повтор проверки остаются доступны, серверная проверка обязательна.

1. Сохранить существующий домен, HTTPS и origin редактора: локальные пользовательские проекты остаются в своём браузере. Каталог не мигрирует и не очищает их хранилища.
2. Задать серверные `CATALOG_SECRET`, `CATALOG_TELEGRAM_BOT_TOKEN`, `CATALOG_ORIGIN=https://gridstudio.me`. Убрать `CATALOG_DEV=1`. Production-запуск отказывает при HTTP origin или слабом серверном секрете. ALTCHA не требует внешних ключей. При обновлении API добавляет только таблицу captcha_challenges; публикации и аккаунты сохраняются. Ключ веб-модератора обязателен только при явном включении резервного интерфейса.
3. API слушает только 127.0.0.1:4174. Reverse proxy отправляет `/api/catalog/` туда, сохраняет Origin, допускает до 9 МБ для `/api/catalog/spaces/` и до 2 МБ для остальных запросов, перезаписывает X-Forwarded-For реальным адресом клиента. Сам API ограничивает private PUT 8,5 МБ и документ 8 МБ. Только для доверенного proxy включить `CATALOG_TRUST_PROXY=loopback`. Без этого заголовки клиента не используются как IP.
4. `/workshop` отдаёт `catalog.html`; `/workshop/` перенаправляется на `/workshop`, `/catalog` и `/catalog/` — 301 на `/workshop`. Пример reverse proxy и самостоятельного запуска — в README. GitHub Pages этого репозитория публикует только страницу перехода из `github-pages/`; приложение с API размещается на своём сервере.
5. Настроить отдельные постоянные процессы API и Telegram worker (один polling worker на токен; без автоподмены webhook). Убедиться, что runtime включает `assets/fonts`, `assets/portraits`, `scripts/data.mjs` и исходники сервера. Настроить постоянный процесс под непривилегированным пользователем, файловые права, бэкапы и ротацию логов без секретов. Проверить ALTCHA и cookie через HTTPS (при строгой CSP разрешить локальный модуль и blob: Web Worker), затем только по отдельной команде собирать/деплоить.

Документация: [ALTCHA на своём сервере](https://altcha.org/docs/integration/server/), [одноразовость и лимиты](https://altcha.org/docs/integration/security-recommendations/), [Node SQLite](https://nodejs.org/api/sqlite.html).

## Доставка и восстановление Telegram

Заявки уже лежат в транзакционной SQLite до обработки worker. Он обнаруживает pending-ревизии и неразобранные жалобы, создаёт по ним уникальные задания в `telegram_reviews`. `telegram_runtime` хранит offset обновлений и lease. Перезапуск не теряет очередь и не создаёт повторных карточек.

Telegram sendPhoto не имеет idempotency key. Если ответ на отправку потерялся, задание становится `uncertain` и **не отправляется автоматически повторно**: карточка могла дойти. Нажатие её кнопки восстанавливает квитанцию и выполняет решение. Для ошибки 429 применяется retry_after; достоверные 4xx остаются `failed`. После решения обновление подписи карточки повторяется отдельно от публикации в каталоге.

Проверить доставку: `npm run catalog:bot -- --status`. Для uncertain/failed сначала проверить топик вручную; только если карточки действительно нет, выполнить `npm run catalog:bot -- --retry=ID` (команда также запускает worker). Не делать этого, пока другой worker работает. В логах нет токенов, содержимого сеток или ссылок владельцев. Не включать `DEBUG=puregram:*` на production: подробные логи SDK могут содержать данные заявок.

## Проверено локально

183 теста проходят. Для ALTCHA проверены реальные вычисленные решения, неверные подписи/сложность, привязка к браузеру и действию, истечение срока, конкурентный повтор, сохранение реестра после перезапуска, квоты выдачи и обязательность проверки в HTTP-сценарии. Повтор запроса создания после потери ответа по прежнему ID/ключу возвращает существующую квитанцию без новой публикации.

В браузере: отправка из окна скачивания, получение ссылки, вход модератора, одобрение, публичная карточка, добавление в редактор второй сеткой, «Мои публикации», мобильная форма и каталог на 390 px без горизонтального переполнения. Использовалась отдельная локальная QA-база, не реальные публикации пользователей. Production build не запускался.

«Мои публикации» (`?mine=1`) используют общие `catalog-heading`, `catalog-grid`, `catalog-card-art` и `catalog-card-info`: размеры заголовков, карточек, превью и адаптивные колонки совпадают с «Новыми» и «Популярными». Под названием остаются статус, дата и действия управления/скачивания/просмотра; гостевые заявки имеют тот же вид и ссылку привязки. `OwnedPublications.jsx` лениво читает `/manage/:id` через сессию или гостевой ключ; превью непроверенных заявок не открываются публично. Ошибка чтения оставляет карточку и кнопку повтора, ключ не удаляется. Компонент проверен отдельно на тестовых данных; реальные заявки для этой проверки не отправлялись.

После успешного лайка `Gallery.updateLike` обновляет только `liked` и `likes` соответствующей карточки. Он не запускает повторный запрос списка и не размонтирует превью. Порядок «Популярных» остаётся стабильным до следующего запроса при переходе между вкладками/страницами или фильтрации. На изолированном UI-стенде проверены лайк и снятие лайка: счётчики запросов и удалённых canvas не меняются; размеры общих и личных карточек совпадают на 1280 и 390 px.

Telegram: 13 дополнительных тестов с подставным API, включая обычного участника, отказ постороннему, гонки кнопок, изменённые/удалённые ревизии, потерянный ответ, 429, перезапуск SQLite, жалобы и отключение web-модерации. Проверен реальный read-only доступ @grid_studio_bot к чату, права администратора и настройки topic 6. PNG отрисован и просмотрен локально. Тестовые сообщения в рабочий чат не отправлялись; реальное нажатие кнопок ещё не проверено в Telegram.

# Версии и публикация GridStudio

Порядок принят пользователем 28.09.2026. Разработка локально. `npm run dev`, `npm run check`, `npm test` и `npm run release:check` не публикуют проект и не создают production build.

## Версии

Проверить захват пустой середины выделенного арта на обоих холстах, приоритет углов трансформации и перестановки героев, Shift-сдвиг незавершённой фигуры и продолжение рисования после отпускания. `draft-manipulation.test.cjs` проверяет все геометрические инструменты, повёрнутую рамку, привязку, границы, сохранение кистевых ограничений и одну операцию отмены. Эти изменения не требуют миграции.

Проверка каталога после лайков: карточки/превью не размонтируются, список не запрашивается повторно, счётчик выбранной работы обновляется. «Мои публикации» совпадают по размерам с общим каталогом на десктопе и 390 px; авторские действия остаются. Проверено на изолированном стенде с фиктивными аккаунтом и публикациями.

Локальная проверка анимаций: открыть/закрыть инструкцию экспорта мышью и Enter, изменить направление повторным нажатием, открыть вложенный пункт Steam; проверить узкий экран, вкладки каталога и возврат к файлам. Раскрытие большого спойлера занимает около 550 мс с мягким стартом; стрелка использует ту же длительность и кривую. При reduced motion спойлеры переключаются сразу. Изменения только интерфейсные, сборка и миграция данных не нужны.

Локальная проверка перехода с лендинга: «Создать свою сетку» сразу открывает пустой файл, reload не создаёт дубль, прежние файлы остаются. Для карточек публикаций проверить превью владельца и гостя, статусы, недоступный сервер и мобильную ширину. Эти изменения не требуют миграции данных и остаются в Unreleased до команды на сборку.

Источник номера — `package.json`; Vite подставляет его в справку редактора. Согласованная разметка: 1.0 — единая студия; 1.1 — рисование и ASCII; 1.2 — дизайн и сайт; 1.3 — сложные сетки; 1.4 — сохранение и восстановление. Подготовленный общий выпуск — **1.4.0** (`releases/1.4.0.json`), включая последующие готовые каталог, аккаунты и доработки. Не пересчитывать номер заново от старого значения package.json. **1.4.1** (29.09.2026) — патч без изменения формата: нагрузка на API и трафик, повтор облачной отправки, выкладка без поломки открытых вкладок (`releases/1.4.1.json`). **1.5.0** (29.09.2026) — мастерская вместо каталога, свои готовые арты, превью как в Dota, новые способы «Изображение в ASCII», объединение строк при скачивании и оптимизация категорий (`releases/1.5.0.json`); миграция сервера только добавляет таблицы, проверка обновления с 1.4.1 — в docs/project-storage.md. На проде нужен `CATALOG_ADMIN_TELEGRAM_IDS` и nginx с `/workshop`. Подробная ретроспектива сохранена в CHANGELOG.md; исторические теги не создаются задним числом. Пользователь разрешил сборку, GitHub/PR, обновление сайта и Telegram-публикацию 28.09.2026.

- Patch: исправления без изменения формата проекта.
- Minor: совместимые новые возможности.

Номер версии приложения не является номером схемы проекта, ключа localStorage или базы IndexedDB. Их нельзя менять вместе с каждой версией.

## Обычная работа

Поиск папки Steam в экспорте использует существующий API через `/api/catalog/steam/resolve`. Серверу нужен исходящий HTTPS к steamcommunity.com; при добавлении необязательного STEAM_WEB_API_KEY также к api.steampowered.com. Для применения backend-изменения нужен перезапуск API, бот не затрагивается. Прямой код друга и цифровой профиль работают в браузере без API. См. docs/steam-folder.md.

Формат Telegram-карточек модерации обновлён в локальном коде: кастомные эмодзи в HTML-подписи и `icon_custom_emoji_id` в inline-кнопках. После разрешённого обновления worker новые карточки используют новый вид; уже отправленные обновляются при обработке решения. Для этой правки worker не перезапускался, массовое обновление карточек и тестовая рассылка не выполнялись. Очередь и проверки доступа не менялись.

Каталог добавляет отдельный Node API и постоянную SQLite-базу; они не входят в статический dist. Базу `.catalog-data`, `.env.catalog.local` и ключ модератора не включать в Git, артефакты или сменяемые директории релизов. Публичный запуск требует постоянный CATALOG_SECRET и HTTPS-origin. ALTCHA обслуживается на том же домене; отдельные ключи не нужны. API добавляет таблицу captcha_challenges без замены существующих данных; установить зависимости из lockfile и проверить локальный виджет/worker через HTTPS перед выкладкой. Схема выкладки и проверки — docs/catalog.md. Подготовка этих файлов не разрешает запуск сборки, изменение сервера или публикацию.

Необязательный вход через Telegram добавляет в ту же SQLite аккаунты, хеши сессий, личные файлы, аватары и лайки. Перед обновлением сохранять резервную копию всей базы; таблицы и старые публикации не удалять. Worker обслуживает личный вход (включая фото профиля) и модерацию. Проверить соответствие `CATALOG_TELEGRAM_BOT_USERNAME` токену. Для `/api/catalog/spaces/` reverse proxy должен пропускать до 9 МБ, для публичных отправок остаётся лимит 2 МБ. Старый браузерный проект сохраняется как workspace `legacy`, исходный ключ не меняется. По решению пользователя гостевые файлы автоматически привязываются при входе; проверить прерванную отправку, повтор без дублей и сохранение локальных копий. См. docs/accounts-workspaces.md.

1. Менять исходники локально, обновлять раздел Unreleased в CHANGELOG.md.
2. Проверять синтаксис, тесты и интерфейс через dev server.
   Проверить reload в открытом файле с несколькими сетками и после возврата в «Файлы», а также независимость двух вкладок. Навигация хранится отдельно в sessionStorage, миграция документов не требуется.
   Проверить единую кнопку «Изменения сохранены»: открытие версий, состояние ожидания аккаунта и сохранение предупреждения при локальном сбое. На телефоне версии открывает иконка часов; доступ также остаётся в справке.
   Для превью файлов проверить документ с несколькими сетками: актуальные черновики, переход точками/стрелками и открытие выбранной сетки. Хранилище и API этим изменением не мигрируются.
3. Дополнять черновик сводки. `npm run telegram:preview -- releases/draft.json` только печатает разметку, ничего не отправляет.
4. Не запускать build, не трогать сервер, не пушить и не отправлять релизные сообщения без соответствующей команды пользователя.

## После команды «собери»

1. Уточнить фактический номер по текущему package.json и тегам, не повторять уже выпущенный номер.
2. Например, `npm version 1.0.1 --no-git-tag-version` обновляет package.json и lockfile. Само по себе не коммитит, не собирает и не публикует.
3. Перенести готовые пункты из Unreleased в раздел версии, согласовать ту же версию в JSON сводки.
4. `npm run check`, `npm test`, `npm run release:check`, затем `npm run build`.
5. Проверить именно этот dist, сохранить номер версии и SHA исходного коммита в описании сборки. После изменений исходников снова собрать только в рамках одобренной работы.

### Выкладка без потери работы

Работа пользователей хранится в их браузерах (IndexedDB и localStorage) и в серверной SQLite. Выкладка не должна трогать ни то, ни другое:

1. Резервная копия базы перед переключением, с проверкой `PRAGMA integrity_check`.
2. Сборка соответствует коммиту: сначала commit, затем `npm run build`, выкладываются исходники этого коммита и этот dist.
3. Хешированные файлы `assets/` прошлой версии остаются на сервере (копирование без перезаписи). Вкладка, открытая до обновления, продолжает работать на старом bundle и подгружает свои ленивые чанки и шрифты до обычной перезагрузки. Принудительная перезагрузка, `Clear-Site-Data` и очистка хранилищ запрещены.
4. API остаётся совместимым с клиентом прошлой версии: старые маршруты и форматы ответа не удаляются в том же релизе, где появляется замена.
5. Переключение атомарное; если API не отвечает после перезапуска, возвращается прошлая версия. Перезапуск API занимает около секунды: неудавшаяся отправка файла в аккаунт повторяется сама (`openWorkspace`, до 6 попыток за ~2 минуты), локальная копия при этом уже сохранена.
6. Ключи хранилища (`dota-grid-studio.document.v1`, IndexedDB `gridstudio-projects` v1, `gridstudio.workspace.*`) не меняются; тест в `project-storage.test.cjs` это закрепляет.

CI `test.yml` проверяет push/PR без сборки. `build.yml` создаёт артефакт только через ручной workflow_dispatch, проверяет введённую версию и не деплоит сайт. `deploy-pages.yml` также запускается только вручную, но публикует только папку `github-pages/`: сообщение о переезде и кнопку на gridstudio.me. Зависимости и сборка приложения для этой страницы не нужны. В Settings → Pages источником должны быть GitHub Actions; старые ссылки с якорями показывают ту же страницу. Основной index.html и сборка для собственного домена остаются независимыми. Запускать сборку или деплой агент может только по соответствующей команде пользователя.

## GitHub и авторство

Аккаунт участника: `justkiddingxd`. Upstream: https://github.com/linsisss/dota2-grid-toolkit.

Без прав на запись: fork → ветка `codex/release-VERSION` → commit/push в свой fork → Pull Request в upstream. Владелец проверяет PR и делает merge. Сам Approve не добавляет коммиты в основную ветку; вклад учитывается после merge с корректным авторством. Email коммитов должен быть привязан к GitHub-аккаунту, можно использовать его GitHub noreply email. При squash проверить сохранение автора. Contributor — не то же самое, что collaborator с правом push.

Нельзя угадывать email/учётные данные, форсировать push, перезаписывать main или автоматически сливать PR. До первой публикации проверить аутентификацию `justkiddingxd`, создать/найти fork, получить актуальный upstream и сравнить историю. Текущая локальная ветка исторически называется `feat/unified-grid-studio`; автоматически не переименовывалась. В upstream уже есть новые коммиты, поэтому нельзя считать локальный origin/main актуальным.

Перед commit: просмотреть `git diff --cached`; выбирать публичные исходники явно, не `git add .`. Локальный приватный project.md, deploy/, docs/deployment.md, exports/, test-results/, токены и .release-state не публиковать. Для project.md использовать отдельно очищенную версию из for_github с первой строкой `<!-- GridStudio public project context -->`. `npm run release:check` разрешает этот проверенный документ и пустой шаблон `.env.example`, проверяет остальные staged-пути и похожие на токены Telegram строки, но не заменяет просмотр диффа. Не переносить маркер в приватный документ.

Каждый одобренный build должен соответствовать исходному commit и тегу `vVERSION` в репозитории выпускающего. Собранный dist распространять как артефакт или ZIP GitHub Release, а не коммитить node_modules/dist в исходники. Создание GitHub Release, push и PR — после разрешения пользователя на публикацию.

## Telegram: только rich message через puregram

Форум: `-1004309207941`; топик Builds: `2`; логотип: `5316617119524236973`.

Используется **sendRichMessage**, не sendMessage с обычным HTML. Заголовок `<h1>` содержит custom emoji и «Обновление VERSION». Пункты — настоящие task list items `<li><input type="checkbox" checked>`, подпункты — вложенный `<ul>`. В конце ссылка на опубликованный commit/PR/release на GitHub. Токен не передаётся в браузер.

1. Токен в `TELEGRAM_BOT_TOKEN` или игнорируемом `.env.release.local`; пример — `.env.example`. Файл с токеном нельзя копировать в for_github.
2. Предпросмотр: `npm run telegram:preview -- releases/draft.json`.
3. После разрешения опубликовать релиз: сначала commit/push/PR на GitHub, затем добавить реальную `githubUrl` и проверить номер версии.
4. Отправка: `npm run telegram:preview -- releases/draft.json --send --approved`.

Скрипт проверяет совпадение версии с package.json, наличие GitHub-ссылки, формат и размер сводки. Квитанция с message ID пишется в .release-state. Повтор той же версии автоматически запрещён. При таймауте квитанция остаётся pending: сначала проверить чат, не удалять её ради слепого повтора. Обычные сетевые повторы отключены.

Тест имеет явный `test: true`, не считается релизом и не требует GitHub-ссылки. Отправлять тест можно только по просьбе пользователя: `npm run telegram:test -- --send`. Исправление своего ранее отправленного теста: добавить `--edit-test=MESSAGE_ID` (ID сверяется с локальной квитанцией). Опубликованный пост релиза исправляется на месте, без второго уведомления, только с разрешения пользователя: `--send --approved --edit-release=MESSAGE_ID` — сообщение должно совпадать с квитанцией этой версии. Сводка может делиться на разделы (`sections: [{ title, changes }]`), каждый — свёрнутый блок `<details>`. 28.09.2026 тест №17 в топике 2 отправлен и затем заменён на rich message; API подтвердил rich_message и custom emoji. Новая сборка при этом не публиковалась.

Справка: [GitHub contributions](https://docs.github.com/en/account-and-profile/reference/profile-contributions-reference), [fork и Pull Request](https://docs.github.com/en/get-started/exploring-projects-on-github/contributing-to-a-project), [Telegram rich messages](https://core.telegram.org/bots/api#rich-messages), [puregram](https://github.com/puregram/puregram).

### Каталог: Telegram worker

При проверке редактора проверить перетаскивание героев между рядами, отмену вне группы и Ctrl+Z/Ctrl+Shift+Z. Оно меняет только порядок `hero_ids`, без миграции документов. Геометрия, повторяющиеся ID, reduced motion и завершение анимации проверяются в `tests/hero-order.test.cjs`.

Лимиты публикаций: 3 гостевые / 10 аккаунтных отправок за скользящие 24 часа, 60 с IP. Обновление API добавляет только индексы `works_account` и `audit_work_action_at`; прежняя история учитывается автоматически. Базу, аудит и счётчики не сбрасывать. Проверка: `tests/catalog-limits.test.cjs` (переход от гостя к аккаунту, старые записи и удаления, перезапуск, реальный Retry-After, сохранение ALTCHA и idempotency).

Модерация использует тот же puregram-бот, но другой топик: approve grids here, ID 6, чат -1004309207941. Это обработка заявок пользователей, отдельно от релизных объявлений в topic 2. Production требует отдельного постоянного процесса `npm run catalog:bot` рядом с API и общей SQLite, с production-зависимостями puregram/@napi-rs/canvas и локальными assets/fonts, assets/portraits. Worker запускается один раз на токен; local polling нужно остановить перед запуском production с тем же токеном. Реальные сборка, обновление PR и деплой этим изменением не выполнялись.
